# AGENTS.md

## 목적

이 문서는 `review-calendar-web` 프로젝트의 현재 기준 문서다.
새 채팅에서 작업을 시작할 때도 가장 먼저 이 문서를 확인하고, 여기 적힌 현재 동작과 UX 규칙을 기준으로 이어서 구현한다.

## 프로젝트 정의

여러 체험단 사이트에서 선정된 체험단 링크를 등록하고, 체험 가능 기간, 확정 일정, 리뷰 마감일을 캘린더 중심으로 통합 관리하는 다꾸 감성 서비스다.

## 기술 스택

- 프론트엔드: `Next.js App Router`
- 언어: `TypeScript`
- DB: `PostgreSQL` via `postgres`
- 개발 서버: `http://localhost:3005`

## 환경변수

- `DATA_GO_KR_SERVICE_KEY`
  - 공공데이터포털 한국천문연구원 공휴일 API 인증키
- `DATABASE_URL`
  - PostgreSQL 연결 문자열
  - 로컬 개발과 Vercel/Neon 배포 환경에 각각 설정한다.

## 저장 구조

- 체험단 / 사이트 등록 DB: `PostgreSQL`
- 앱 로그인 세션: HttpOnly 쿠키 + `user_sessions`
- 외부 체험단 사이트 로그인 세션은 사용하지 않는다.

## 현재 핵심 기능

### 0. 앱 로그인

- 사용자는 앱 계정으로 로그인한 뒤 서비스를 사용한다.
- 로그인은 이메일이 아니라 `아이디 + 비밀번호`로 한다.
- 회원가입은 `아이디 중복 확인`, `비밀번호`, `비밀번호 확인`, `이메일 인증번호 확인`을 거쳐 진행한다.
- 이메일은 로그인 식별자가 아니라 인증번호 수신 및 계정 확인 용도로 사용한다.
- 비밀번호는 평문으로 저장하지 않고 서버에서 해시하여 저장한다.
- 로그인 상태는 HttpOnly 세션 쿠키와 `user_sessions` 테이블 기준으로 관리한다.
- 로그인하지 않은 사용자는 체험단, 사이트 등록, 공휴일 API를 사용할 수 없다.
- 체험단 / 사이트 등록 데이터는 `userId` 기준으로 분리한다.

### 0-1. 공개 파싱

- 체험단 링크 등록 API는 Vercel 서버에서 공개 정보를 바로 파싱하고 `campaigns`에 저장한다.
- 별도 자동화 워커를 사용하지 않는다.
- 로그인 세션이나 Playwright 없이 공개 HTML/API에서 접근 가능한 정보만 파싱한다.

### 1. 사이트 관리

- 사용자는 체험단 사이트 이름과 사이트 주소를 직접 추가할 수 있다.
- 로그인 페이지 주소는 받지 않는다.
- 외부 체험단 사이트 로그인 연동은 사용하지 않는다.
- 사이트 등록 자체는 범용이다.
- 상세 파싱은 사이트별 공개 파서 확장 구조다.
- 현재 공개 파서가 구현된 사이트는 `리뷰노트`, `강남맛집`이다.
- 아직 파서가 없는 도메인도 사이트 목록에는 등록할 수 있지만, 자동 등록은 `자동 등록 준비 중` 상태로 막는다.
- 사이트 목록에 없는 도메인 링크는 체험단 등록이 불가능하다.

### 2. 체험단 등록

- 사용자는 선정된 상세 링크와 업체 연락처를 입력한다.
- 업체 연락처는 항상 사용자가 직접 입력한다.
- 프로그램은 사이트 등록 목록과 도메인을 확인한 뒤, 해당 도메인의 공개 파서가 준비된 경우 자동 파싱하여 DB에 저장한다.
- 파서는 제목, 제공내역, 체험 기간, 리뷰 마감일, 주소, 안내 메모 등 공개로 접근 가능한 정보를 가져온다.
- 화면에는 실제 링크로 등록된 체험단만 보여야 하며, 샘플 더미 체험단은 두지 않는다.

### 3. 캘린더 일정 확정 흐름

- 일정 확정은 `체험단 선택 기반`이 아니라 `날짜 클릭 기반`이다.
- 사용자가 캘린더 날짜를 클릭하면 팝업이 열린다.
- 팝업에는 `이 날짜에 체험 가능한 체험단`, `이미 확정된 체험단` 영역이 있다.
- `체험 확정`을 누르면 `selectedDate`가 해당 날짜로 저장되고 상태는 `scheduled`가 된다.
- `확정 취소`를 누르면 `selectedDate = null`, 상태는 `unscheduled`가 된다.

### 4. 후속 상태 흐름

- `unscheduled`: 날짜 미정
- `scheduled`: 날짜 확정
- `completed`: 체험 완료
- `review_submitted`: 리뷰 완료

취소는 항상 바로 이전 단계로 돌아간다.

- `확정 취소`: `scheduled -> unscheduled`
- `체험완료 취소`: `completed -> scheduled`
- `리뷰완료 취소`: `review_submitted -> completed`

### 5. 탭 구조

- `캘린더`
- `선정체험단`
- `체험완료`
- `리뷰완료`

### 6. 공휴일 표시

- 공휴일 데이터는 공공데이터포털 한국천문연구원 `SpcdeInfoService/getRestDeInfo`를 기준으로 동기화한다.
- 캘린더에는 공휴일 이름을 날짜 칸 안에 직접 표시한다.
- 공휴일 동기화가 실패해도 체험단 기능 자체는 멈추지 않아야 한다.

## 캘린더 표시 규칙

- `unscheduled` 체험단만 `체험 N건`
- 리뷰 마감일이 해당 날짜인 체험단만 `마감 N건`
- `scheduled` 이고 확정 날짜가 해당 날짜인 체험단만 `방문 확정 N건`
- `completed`, `review_submitted` 상태 체험단은 캘린더에 표시하지 않는다.

## 선정체험단 카드 레이아웃 규칙

- 상단: 사이트 배지 + 상태 배지
- 중단: 체험단 제목 + 제공 내역
- 하단: `체험 기간 / 리뷰 마감 / 확정 일정` 3칸 정보 박스

## UX 규칙

- 프로토타입 느낌 문구는 사용하지 않는다.
- 실제 운영 서비스처럼 바로 이해되는 한국어 문구를 사용한다.
- `픽` 대신 `확정` 표현을 사용한다.
- 버튼 안 텍스트는 절대 두 줄이 되면 안 된다.
- 클릭 가능한 카드 내부에 액션 버튼이 들어가는 경우 중첩 `<button>` 문제가 생기지 않도록 처리한다.

## 데이터 반영 규칙

아래 동작은 모두 DB 반영 + 화면 즉시 반영이 함께 이뤄져야 한다.

- 체험단 등록
- 사이트 추가 / 제거
- 일정 확정
- 확정 취소
- 체험완료 처리
- 체험완료 취소
- 리뷰완료 처리
- 리뷰완료 취소

## 사용자 DB 보호 규칙

- 사용자가 실제로 작업 중인 DB 데이터는 절대 임의로 건드리면 안 된다.
- 사용자 동의 없는 삭제, 초기화, 테스트 데이터 삽입은 금지다.
- 기존 데이터 구조 변경은 데이터 손상이 없도록 보수적으로 진행한다.

## 현재 주요 API

- `GET /api/bootstrap`
- `POST /api/auth/register`
- `POST /api/auth/login`
- `POST /api/auth/logout`
- `GET /api/auth/me`
- `GET /api/auth/check-username`
- `POST /api/auth/send-email-code`
- `POST /api/campaigns`
- `PATCH /api/campaigns/[id]/schedule`
- `PATCH /api/campaigns/[id]/status`
- `GET/POST/DELETE /api/site-connections`

## 새 작업 시작 규칙

1. `review-calendar-web/AGENTS.md`를 먼저 확인한다.
2. 현재 요청이 이 문서의 기준과 충돌하는지 확인한다.
3. 충돌하지 않으면 그대로 확장 구현한다.
4. 충돌하면 사용자와 기준 변경을 먼저 합의한다.

## 문서 관리 규칙

- 기본 운영 기준 문서는 `review-calendar-web/AGENTS.md` 하나로 관리한다.
- 추가 `.md` 문서는 사용자가 명시적으로 요청할 때만 만든다.
- 임의로 상세 문서를 계속 늘리지 않는다.
